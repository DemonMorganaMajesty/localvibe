# 缓存穿透、缓存击穿、缓存雪崩完整梳理

## 基础概念


缓存穿透：查询不存在的数据（如 id=-1），缓存和 DB 都查不到，导致每次都穿透到 DB。

解决：① 缓存空对象（null）并设置短过期；② 布隆过滤器（Bloom Filter） 在查询前置过滤，极大概率拦截不存在 Key。

缓存击穿：热点 Key 突然失效，海量并发请求同时打到 DB。

解决：① 使用互斥锁（Mutex），只有第一个线程去查 DB 并重建缓存，其他线程等待；② 逻辑过期（不设置 TTL，后台异步更新）。

缓存雪崩：大量 Key 同时过期，或 Redis 宕机，导致流量全部涌向 DB。

解决：① TTL 增加随机偏移量（如 ±5min）；② 主从 + 哨兵保证 Redis 高可用；③ 本地缓存（ehcache）做二级兜底 + 限流降级（Sentinel/Hystrix）。


1. **缓存穿透**
   查询**数据库根本不存在**的数据（id=-1、9999999），Redis查不到，请求直接穿透到MySQL。恶意大量请求不存在ID，数据库压力飙升。
   解决手段：缓存空对象（项目实现）、布隆过滤器（项目未实现）。
2. **缓存击穿（热点key问题）**
   **某一个热点key**缓存失效一瞬间，海量并发请求同时涌入，全部绕过缓存访问数据库，压垮DB。

> 和雪崩区分：只针对**单个热点key**。
> 解决手段：Redis互斥锁（同步重建，阻塞）、逻辑过期（线程池异步重建，返回旧数据，不阻塞）。

3. **缓存雪崩**
   **大批量缓存key同一时刻集体过期**，大量请求全部打到数据库；也包含Redis服务宕机引发的雪崩。

> 和击穿区分：是**大量key集体失效**，不是单个key。
> 解决手段：TTL增加随机偏移打散过期时间、多级缓存架构、缓存预热、限流降级、Redis集群高可用。

## 对应文件

文件：**ShopServiceImpl.java**

- `selectByIdWithCacheThrough()`、`selectWithMutex()`、`selectWithLogicExpire()`：三个演示Demo，仅用于学习理解缓存问题，业务接口完全不调用。
- `selectById()`：项目真实业务调用的查询方法，L1+L2多级缓存，底层依赖`CacheClient`工具类。

## 各个问题在代码里的坑点

1. `selectByIdWithCacheThrough`：只做缓存空对象，热点key过期直接击穿DB；TTL固定，有雪崩隐患。
2. `selectWithMutex`：互斥锁会造成大量请求阻塞排队，用户体验差，不适合超高并发；无TTL随机偏移，雪崩没解决。
3. `selectWithLogicExpire`：**无法防护缓存穿透**，传入不存在id会直接访问数据库；仅保护当前热点key，其他普通key雪崩依旧存在。
4. 线上`selectById`：虽然有完整防护，但Pub/Sub有缺陷，服务离线时缓存失效消息丢失，Caffeine本地缓存只能等待TTL过期，会短暂存在脏数据。

## 面试口述完整版

> 缓存穿透是查询数据库不存在的数据，请求绕过缓存打MySQL，我项目使用缓存空对象来解决，布隆过滤器没有落地。
> 缓存击穿是单个热点key缓存失效，瞬间大量并发打到数据库，有两种方案：互斥锁，同步重建缓存，但是会阻塞用户；逻辑过期，开启线程池异步后台更新缓存，接口直接返回旧数据，性能高，但是会存在短暂数据不一致。
> 缓存雪崩是大批量缓存key同时过期，大量请求同时压数据库，解决方案给TTL加上随机偏移打散过期时间，再搭配多级缓存架构做兜底。
> 项目前面三个是手写的演示demo，生产没有使用；线上实际使用selectById，采用Caffeine本地缓存作为L1，Redis作为L2二级缓存。底层CacheClient工具类内部实现缓存空对象解决穿透，逻辑过期异步重建解决击穿；TTL追加随机偏移，多级缓存共同缓解缓存雪崩。更新数据的时候删除Redis缓存，通过Redis Pub/Sub通知全部服务实例清除本地Caffeine缓存。
> 同时也要知道这套方案的短板，Redis Pub/Sub消息不持久化，如果实例离线，缓存失效通知丢失，本地缓存只能等待TTL过期，会短暂存在脏数据，Canal会作为二次兜底。
